02 / Build workflow YAML — important

Private build configuration · Existing file

.github/workflows/main.yml

This is the actual workflow we used for the successful Windows build. It is stored in the private OptionsPlotter-build repository. You do not create a new YAML file for every release; maintain this existing one.

Open main.yml in GitHub ↗ · Run this workflow ↗

What the YAML does: runs on windows-latest when manually triggered (workflow_dispatch), sets up Python 3.11, installs PyInstaller / Matplotlib / ib_insync and Inno Setup, packages the Python script into OptionsPlotter.exe, creates an Inno Setup installer, then uploads OptionsPlotter_Setup_v1.0.0.exe into a private draft release using gh release create. It avoids the Actions artifact-storage quota issue we hit.

For future versions: before running the workflow, open main.yml and update all version-specific values, not just the GitHub Release title. Otherwise the build may package an old source file or label the installer with the wrong version.
  • Source filename: change the filename at the end of the python -m PyInstaller command if you uploaded a differently named .py file.
  • Installer version: update AppVersion=1.0.0 in the generated Inno Setup script.
  • Installer filename: update OutputBaseFilename=OptionsPlotter_Setup_v1.0.0.
  • Upload path: update $file = 'installer/OptionsPlotter_Setup_v1.0.0.exe' so it matches the new filename.
  • Website redirect: after publishing the public release, update OptionsPlotter/download/index.html to reference the new installer filename.

The YAML also uses permissions: contents: write so its GitHub token can create the private draft release. Do not switch back to actions/upload-artifact unless artifact storage is available.

03 / Release steps

1

Update the private Python source

Upload or replace the intended application source in OptionsPlotter-build. Open .github/workflows/main.yml and confirm the PyInstaller command references the correct source filename and the installer version/name matches this release.

v1.0.0 source: Options_Plotter_Pro_v12_10_4_Modern_Share_Popup.py

2

Run the Windows installer workflow

Go to Actions → Build Options Plotter Installer → Run workflow. Wait for a successful green checkmark.

The working workflow uses PyInstaller + Inno Setup, then uploads the installer to a private draft GitHub Release rather than Actions artifacts.

3

Download the private installer

Open the newly created draft release from the workflow output or its direct draft-release link. Download OptionsPlotter_Setup_v1.0.0.exe.

Draft releases may not appear in the ordinary Releases listing. Use the direct draft-release link shown by the build workflow.
4

Install and smoke-test

Run the installer on Windows. Confirm the app opens and test the P&L chart, drag-to-price interaction, date slider, and broker connection. The installed package contains OptionsPlotter.exe and _internal dependencies, not the original readable .py file.

5

Create or edit the public GitHub Release

Open public Releases. For the first release, use tag v1.0.0, title Options Plotter v1.0.0 — Free Beta, and your release description. Mark as Latest and leave Pre-release unchecked.

For an existing release, choose Edit rather than creating a duplicate.

6

Attach the installer — required!

Under Attach binaries, upload the Windows installer OptionsPlotter_Setup_v1.0.0.exe. Publish or update the release.

We encountered a GitHub 404 because the public release existed but the installer asset had not yet been uploaded. Always verify the .exe appears under Assets.
7

Confirm the public direct download

The version-specific GitHub installer link must work in a browser where you are not logged into GitHub.

https://github.com/MarkB2026/OptionsPlotter/releases/download/v1.0.0/OptionsPlotter_Setup_v1.0.0.exe
8

Use the branded website redirect

The public repository contains download/index.html, which redirects visitors to the GitHub installer. After GitHub Pages deploys, the branded customer link is:

https://optionsplotter.com/download/

This is a simple redirect, not a download proxy: GitHub may still appear in download details or the browser address during a failed download.

9

Connect the website buttons

In the public website's root index.html, point Free Beta download buttons to /download/.

<a href="/download/">FREE BETA — DOWNLOAD NOW</a>
10

Test the entire public journey

Open an incognito/private browser, visit optionsplotter.com/download/, and confirm the installer starts downloading without a GitHub login. If the redirect page returns 404, check the GitHub Pages deployment status; if GitHub's download URL returns 404, verify the release asset filename.

05 / Future version updates

When you release v1.0.1 or later

Repeat the build → test → publish → verify process with the new version tag and matching installer filename. Update download/index.html when the installer filename changes. The latest release path follows the newest release, but it does not automatically discover a renamed .exe asset.

Release titles and descriptions can be edited any time. Keep existing tags stable once published.

Leave working infrastructure alone: no GitHub username change, no DNS edits, and no Cloudflare or Bitcoin checkout changes are needed for routine releases.

06 / Bitcoin checkout & local session recovery — reuse for every product

Website checkout · Browser persistence · Cloudflare verification

Why we built this

Customers may close the payment popup, refresh the website, navigate away, or return later while a Bitcoin payment is pending. A temporary UI-only checkout would lose the quote, BTC amount, destination address, and transaction ID. The checkout therefore saves its recoverable session in the visitor's own browser using localStorage.

Important distinction: this is browser-local storage on the customer's computer, not a session file inside the installed Windows plotter. It survives ordinary refreshes and browser restarts in the same browser/profile, but it is not guaranteed across devices, private browsing, cleared site data, or disabled storage. The Cloudflare backend remains authoritative for payments and licenses.

What the Options Plotter website saves

  • Product identifier (the selected edition), so a resumed checkout uses the correct product.
  • Original quote: quote_id, quote_signature, required_sats, required_btc, bitcoin_address, and expires_at.
  • Transaction ID (TXID), checkout phase/status, and local save timestamp.
  • A Resume Payment control appears when a saved checkout is available. Reopening checkout restores the existing quote instead of silently starting over.

The current website code uses localStorage, not cookies, and stores a versioned JSON record. It handles blocked or unavailable browser storage without crashing the checkout.

Expected recovery behavior

A

Quote created

Save the returned quote immediately. Show the same BTC amount, address, and original expiration time when the checkout is reopened. Before a TXID is submitted, the countdown is based on the original quote expiry — never reset it by refreshing the page.

B

Popup closed or browser refreshed

Do not erase an unfinished checkout. Offer Resume Payment, restore the saved details, and allow the customer to continue.

C

TXID submitted

Validate the 64-character hexadecimal TXID, save it before verification, and stop treating the quote countdown as a reason to discard the pending payment. Keep the original quote and TXID available for retry and status checks.

D

Verification interrupted

Keep the checkout recoverable on network failure, timeout, popup close, or page refresh. A failed status request is not proof that payment failed. Let the customer retry verification or check saved status without sending another payment.

E

Confirmed or expired

Use the backend's verified status to decide whether a payment succeeded. Retain appropriate server-side records for recovery and replay protection. Clear or replace local state only when it is safe to do so; never lose an unresolved TXID.

Backend components to preserve

  • Cloudflare Worker: falling-sky-7997.traderrepository.workers.dev — checkout API and verification logic. The public site's code currently calls /premium/verify to verify a submitted TXID and /premium/status?quote_id=… to check saved payment state.
  • Cloudflare KV / D1: persistent payment and license records; keep quote/order identifiers, product mapping, verification outcomes, and replay protections consistent. Confirm the active bindings and schema before cloning to another product.
  • Bitcoin checks: blockchain verification (Blockstream in the existing design), correct receiving address, expected amount, confirmation threshold, and prevention of reusing a TXID for multiple purchases.
  • Timing rules in the established design: 60-minute quote validity, one blockchain confirmation, and the ability to complete verification after expiry when the TXID was registered in time. Verify the deployed Worker actually enforces these rules before launch.
  • Licensing: associate a confirmed payment with the correct product/edition and license or entitlement in D1; the browser's saved state alone never grants access.
Do not store secrets in localStorage. No private keys, signing secrets, API tokens, wallet seed phrases, or privileged license-generation credentials belong in website JavaScript or browser storage. Keep those on the Worker/server side.

Repeat this for each new product

  1. Copy the proven checkout UI, persistence, and recovery logic into the new product website.
  2. Give the product its own product IDs, names, versions, prices, and edition mapping; check both browser catalog and Worker-side catalog.
  3. Choose a distinct localStorage key per product/site, with a versioned record format. Avoid accidentally resuming another product's checkout.
  4. Point the site at the intended Worker API; configure approved site origins/CORS and any required routes or domain settings.
  5. Verify the Worker’s KV/D1 bindings, product-to-license mapping, and idempotent order/transaction handling before accepting real payments.
  6. Test refresh → resume, close popup → resume, browser restart → resume, TXID → network failure → retry, expiry before TXID, confirmation after timely TXID, and duplicate TXID rejection.
  7. Test both same browser recovery and server-side recovery. Local storage alone cannot restore checkout on a different computer or after site data is cleared.
  8. Do not overwrite a pending paid order with a new quote without checking its saved status first.

Current reference files: public OptionsPlotter/index.html (checkout and localStorage recovery) and the existing Cloudflare Worker implementation. Keep a separate private copy of Worker source, configuration, D1 migrations, and KV binding names for repeatable deployments.
